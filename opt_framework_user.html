Optimization Framework in MORIS

OPT Overview

Optimization in MORIS is handled through the OPT module. This is split up into three major components: The optimization problem, algorithms, and criteria interfaces. These are set up and controlled by a fourth component, the OPT Manager. The OPT Manager itself doesn't add any functionality, but it is what takes in all of the parameter list inputs for OPT and orchestrates the whole optimization process.

As a basic MORIS user, you may never actually work with the Manager. OPT Parameter lists are set up just like the other modules, where you need a MORIS cell of MORIS cells of parameter lists. This parameter list structure should automatically be passed to the manager through the MORIS main, and it knows what to do with them. However, the important thing to remember is that ordering of the parameter lists matter.

The outer cell of parameter lists should always be of size 3, corresponding to 3 sets of parameter lists which then build the aforementioned 3 major components of OPT. As a summary:

  1. The first cell of parameter lists (index 0) defines the optimization problem you're trying to solve. There should only be 1 parameter list in this cell, which is the OPT problem parameter list.
  2. The second cell of parameter lists (index 1) defines what other modules or functions will be providing design criteria to OPT, known as a Criteria Interface.
  3. The third cell of parameter lists (index 2) defines the optimization algorithms to be used to solve the problem.

Each of the major components and their inputs are explained in greater detail in the following sections.

OPT Problem

As mentioned in the background/theory section, the objectives and constraints of an optimization problem can depend on both the design variables directly as well as the design criteria . These are the two types of values that OPT knows about. While it is true that perhaps could depend on some field variables which depend on through some sort of system solve such as a finite element analysis, this is not a requirement of a generic optimization problem. Thus, the dependencies of the criteria on the design variables and other factors is handled by the specific use of the OPT module.

Inside of MORIS, the design variables which OPT operates on are referred to as ADVs, or Abstract Design Variables. This is to prevent confusion with PDVs, which other modules may refer to. ADVs are considered abstract because at the point that OPT is operating on these design variables, they have no true physical meaning to the algorithm. They are simply variables which define a design, and what they actually mean is not important to OPT. The design that a set of ADVs produces is handled by an interface to OPT (see next section).

When dealing with constraints, be aware that the OPT problem stores all of the constraints and the respective gradients together. This means that equality and inequality constraint values are all given as a vector, and their gradients are single matrices. OPT distinguishes between equality and inequality and equality constraints through moris::opt::Problem::get_constraint_types() which returns a vector of identifying integers, 0 for equality and 1 for inequality.

The default parameters in the OPT problem parameter list are created with moris::prm::create_opt_problem_parameter_list().

Parameters
is_optimization_problem[false]: Whether or not to construct OPT and run an optimization problem. This acts as a flag for convenience so that OPT parameter lists do not have to be deleted in order to just run a forward analysis.
problem["user_defined"]: The type of problem. Right now only user-defined problems are supported, but in the future if certain optimization problem types become very common, they may be built in as options into MORIS.
finite_difference_type["none"]: Type of finite differencing for gradients. Possible options:
  • "central"
  • "forward"
  • "backward"
  • "none"
finite_difference_epsilons["1E-8"]: Epsilon(s) to use per ADV for finite differencing. This is a string which gets converted into a vector of real values. An epsilon can be provided for each ADV in the problem, or a single value can be provided, in which case that will be applied to all ADVs.
library[""]: Path to a shared object file from which the user-defined problem functions are pulled from. Because only user-defined problems are supported right now, this default must be overridden.

User-defined OPT Problem

Right now, a user-defined problem is the only supported optimization problem type. In a user-defined OPT problem, all of the pure virtual functions needed to inherit from the base OPT Problem are supplied through a linked shared object (.so) file. The path to this file is given through the "library" parameter in the parameter list. This library may be different than that of other MORIS modules, because unlike those other modules, OPT does not rely on any of these other modules and can be used outside of a MORIS workflow.

Since each optimization problem is defined with a single method for computing objectives and constraints, the user-defined functions in the shared object file must have specific names. This also maintains simplicity over having to give function names as well. These are as follows:

  • get_constraint_types (moris::opt::Constraint_Types_Function): Returns a vector of constraint types in the same order that the constraints themselves are provided. 0 Indicates an equality constraint, while 1 indicates an inequality constraint. Note that for compatibility reasons with our algorithms, right now all equality constraints must be indexed before the inequality constraints.
  • compute_objectives (moris::opt::Objective_Constraint_Function): Evaluates the objective. Note that MORIS does not right now support multi-objective optimization, but a single objective is still returned in matrix format to make it consistent for HDF5 output as well as to reduce additional function types.
  • compute_constraints (moris::opt::Objective_Constraint_Function): Evaluates all of the constraints in a vector.
  • compute_dobjective_dadv (moris::opt::Objective_Constraint_Function): Evaluates the explicit gradient of the objective with respect to the ADVs;
  • compute_dobjective_dcriteria (moris::opt::Objective_Constraint_Function) Evaluates the gradient of the objective with respect to the criteria;
  • compute_dconstraint_dadv (moris::opt::Objective_Constraint_Function) Evaluates the explicit gradient of the constraints with respect to the ADVs; and
  • compute_dconstraint_dcriteria (moris::opt::Objective_Constraint_Function) Evaluates the gradient of the constraints with respect to the criteria; and

Adding a New OPT Problem

Some users may want to add problem definitions which are built into MORIS and can be selected using the input parameter list. To do this, create a new class which inherits from the base problem class. Define the pure virtual functions from the base class, which are done similarly to the user-defined case. However, the ADVs and criteria are protected members, and thus are not passed in as input arguments and instead can be accessed directly in these functions. Additional functionality can be added here as needed.

In order to have this new problem type be an option that can be selected through the parameter list, add it to the selection logic in moris::opt::create_problem().

OPT Criteria Interfaces

Right now you might be asking, so where do these ADVs and criteria evaluations come from? This is the job of the OPT Criteria Interface(s) (or just "interface"). OPT is set up to take in interface classes which are able to answer certain questions for providing criteria evaluations and their gradients with respect to design variables. This is done so that OPT can be used by any module, for example you could run a sub-optimization problem within a forward analysis. The MORIS Workflow is an example of a criteria interface, and this is what is used for large optimization problems using finite element analysis in MORIS. Workflows are provided to OPT through the MORIS moris::main().

The default parameters in an OPT criteria parameter list are created with moris::prm::create_opt_interface_parameter_list(). These are as follows:

Parameters
type["user_defined"]: The type of problem. Right now only user-defined problems are supported, but in the future if certain optimization problem types become very common, they may be built in as options into MORIS.
library[""]: Path to a shared object file from which the user-defined interface functions are pulled from. Because only user-defined interfaces are supported right now, this default must be overridden.

The interface parameter lists are different from those defining the optimization problem because there could potentially be multiple interfaces. If only one interface is used, this is trivially the only interface passed into OPT or there will only be one parameter list in the second cell of OPT parameter lists. But if more than a single interface is being used, we require an interface manager. This manager will manage the criteria computations of separate interfaces, and make sure that they are all combined and made available to the OPT problem. However, this requires a few extra parameters, which are defined in the interface manager parameter list. If you are using multiple interfaces, the first parameter list in the cell of interface parameter lists must be an interface manager parameter list, regardless of where the interfaces are coming from . If total number of interfaces that are created externally and internally is greater than one, this rule applies. Defaults for the interface manager parameter list are generated using moris::prm::create_opt_interface_manager_parameter_list(). The parameters for this are:

Parameters
shared_advs[false]: If all of the ADVs are shared between criteria interfaces. While false, the first interface is asked for the initial ADVs, but all interfaces can place upper/lower bounds on these ADVs. The final upper and lower bounds will be the most restrictive out of all bounds provided for each ADV. If this parameter is set to true, each interface is required to provide its own initial ADVs and upper/lower bounds, and the manager will keep track of which ADVs belong to which interface.
parallel[false]: If the manager should perform criteria evaluations in parallel. The default is to ask for criteria and sensitivity vectors from each interface one at a time, in serial.
num_processors_per_interface[""]: List of processors to use per interface. This is a string that is converted into a vector. If the parallel option is set to true, this must be provided, The total number of processors given in the vector must be less than or equal to the number available.

The ADVs and criteria evaluations obtained through these interfaces will be assembled into vectors in the order that they were provided to OPT, starting with the external interface. For example, if a MORIS Workflow provides 2 criteria and a user-defined interface provides 1, the OPT Problem will see a criteria vector of length 3, with the first two being the criteria from the Workflow and the last one being from the user-defined interface.

User-defined OPT Criteria Interface

Right now, a user-defined interface is the only supported OPT interface type through the parameter list. The MORIS workflow interface is obviously supported in OPT, but this is created separately from OPT and passed in later. Similar to a user-defined OPT problem, all of the pure virtual functions needed to inherit from the base OPT Interface are supplied through a linked shared object (.so) file. The path to this file is given through the "library" parameter in the parameter list. This library may again be different than that of other MORIS modules and the OPT Problem.

Following the same pattern as the OPT Problem, the user-defined functions in the shared object file must have specific names. These are:

  • initialize (moris::opt::Criteria_Initialize_Function): Fills 3 matrix references, one for the initial ADVs, one for the lower bounds, and one for the upper bounds.
  • get_criteria (moris::opt::Criteria_Function): Evaluates a vector of criteria. This vector can be any length, and they will all be given to the OPT Problem.
  • get_dcriteria_dadv (moris::opt::Criteria_Function): Evaluates the gradient of the criteria with respect to the advs;

Adding a New OPT Interface

Some users may want to add problem definitions which are built into MORIS and can be selected using the input parameter list. To do this, create a new class which inherits from the base interface class. Define the pure virtual functions from the base class, which are done similarly to the user-defined case. This process is almost identical to adding a new OPT Problem type, but the functions are obviously different.

In order to have this new interface type be an option that can be selected through the parameter list, add it to the selection logic in moris::opt::create_interface().

OPT Algorithms

A general nonlinear optimization problem can be solved by diverse iterative methods, like nonlinear programming or genetic and evolutionary algorithms. For some problems it may be efficient to apply subsequently different methods. For example, a robust evolutionary strategy determines roughly the position of the optimum, then final approach is done by a mathematical programming method with a high convergence rate near the optimum. MORIS does not make any decisions for you about what algorithms will work best for your problem, and it will not automatically combine methods. It is up to you to know your problem and the basic theory of what algorithms might work best. MORIS also currently only supports a limited number of algorithms through external libraries, which are right now all mathematical programming algorithms.

However, MORIS does support the concept of using multiple different algorithms and/or algorithm settings to be used on the same problem. All of the algorithms defined in the third cell of parameter lists are used sequentially on the optimization problem defined above, with one algorithm taking over for the previous one as soon as the previous one has satisfied its stopping criteria. Since each algorithm requires very different parameters, . MORIS also has a "sweep" algorithm, which does not attempt to solve the posed optimization problem, but instead sweeps the possible ADVs between the upper and lower bounds and outputs the objective, constraint, and gradients for the user. This is helpful for doing preliminary studies or debugging a problem setup.

The algorithm types that OPT supports are:

  • Globally Convergent Method of Moving Asymptotes (GCMMA)
  • Limited-Memory Broyden-Fletcher-Goldfarb-Shanno (LBFGS)
  • Sequential Quadratic Programming (SQP)
  • Design Variable Sweep
Note
Adding a new algorithm to MORIS is a much more involves process than adding a new problem or interface type. Therefore, this is left for the developer section about OPT algorithms.
